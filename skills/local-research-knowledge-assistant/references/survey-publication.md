# 调研报告的网站发布

仅在交付阶段接入静态站，或修改已有发布范围时读取。一般离线报告不需要本文件。源文件与构建流程沿用[报告文件与维护](survey-maintenance.md)。

## 自动生成发布清单

使用本地 knowledge_site 发布报告时，网站已支持通用 `.site-publish.json` 协议。新报告沿用维护约定中的目录组织，在报告根目录由生成流程自动写出清单，网站无需为每个主题增加过滤代码。目录是否在 Git 中，与文件是否展示在网站上分开决定。

默认约定：完整 HTML 报告和独立交互图谱属于 `pages`；图表、脚本样式、下载用 Markdown、文献数据和 BibTeX 等读者依赖属于 `assets`；源稿、模板、构建脚本、维护说明及未公开的证据材料不进入发布清单。不要因为扩展名是 `.md` 或 `.html` 就把文件当成阅读入口，也不要同时为完整报告的 HTML 与 Markdown 导出建立重复导航。

清单示意（路径相对报告根目录）：

```json
{
  "version": 1,
  "pages": ["output/report.html", "output/atlas.html"],
  "assets": ["output/report.md", "output/references.bib", "output/literature.json", "output/figures/overview.png"]
}
```

这不是要求用户每次手填的配置表。构建脚本应维护一份产物登记表，生成文件时明确其用途；打包清单与网站清单由同一登记表导出。新增图表或导出文件时只在生成入口登记一次，再自动更新发布清单。上例仅展示结构，实际生成时必须列齐引用资源；不要硬编码某一领域的名称、篇数或图表集合。

网站将 `pages` 建成目录与搜索入口，将 `assets` 保留为原始资源；本协议的报告以 HTML 为阅读入口，资源保持相对路径。未列文件不发布。`.site-publish.json` 必须随报告提交，不能被隐藏文件忽略规则误排除。网站构建负责读取已有清单，不负责重新执行研究报告的 Python 生成器；报告更新后先重建并同步成品和清单。

首次接入时检查实际构建器是否支持该协议；其他静态站采用其等效发布规则，不把此文件名当通用标准。针对当前 knowledge_site，新报告复用一次已经建立的协议即可。验证时确认目录与搜索只出现预期入口、内部文件未进入发布目录、页面资源与下载链接完整；目录命名本身不能代替发布检查。
