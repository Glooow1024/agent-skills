# 论文与技术笔记的写作约定

用于论文笔记和技术文章总结。写论文笔记时结合 [reading.md](reading.md) 的用户模板与成稿取舍；领域调研使用 [survey-writing.md](survey-writing.md)，不套用单篇论文模板。

<a id="tldr"></a>

### TL;DR：技术定位、机制与独特贡献

这是用户对论文和技术总结笔记的写作偏好。TL;DR 应让读者迅速理解技术如何工作及其价值，按内容选择组织方式，不强制条数或套用统一模块清单。

**论文笔记的 TL;DR 先交代应用场景和整体任务**：面向什么使用情境或研究问题，在做什么事；必要时用输入、输出或目标说明任务边界。读者应先理解工作的用途，再阅读模块、机制和创新点。基础或理论工作可说明研究场景与目标，不虚构原文未涉及的落地应用。

- **系统性技术**：先用一句话概括整体体系；再说明关键模块各自的属性、功能与职责，以及模块之间如何协作。模型基础、部署位置、输入输出、通信接口或运行频率等，仅选取对理解体系必要且有资料依据的信息。不能只罗列模块名称而省略数据流、控制流或任务交接关系。
- **单点技术**：先交代它在更大系统或技术流程中的位置和角色，再串起“解决什么痛点/难点 → 核心思想与做法 → 创新点 → 能实现的效果”。角色可以是训练方法、数据处理、感知、规划、控制或评测等，不必虚构完整系统或强行拆分模块。
- **两类都要突出独特贡献**：材料提出了创新、独特的想法、技术或观点时，明确写出它相对已有做法改变了什么、为何产生作用；不要用“更先进、更强、更通用”等评价代替机制。独特性也可能来自模块协作或问题表述，不只来自模型结构。

论文笔记通常采用“应用场景与整体任务概述＋若干机制要点”；混合型工作以主要贡献为主线，可先概括系统再突出其中的单点创新。纯新闻或非技术观点文章按其事件、论点组织，不强塞技术架构。必要数字用于说明机制或效果及其条件，详细实验和局限放正文。

只写有依据的机制、效果与版本关系；推断用“据此推测”等措辞标明，不把未披露接口、部署方式或作者的创新宣称写成已核实事实。用户亲写的 TL;DR 作为偏好示例和人工内容保留，未要求修改时不覆盖；发现事实疑点另行指出。

成稿时检查：读者能否从 TL;DR 开头看出“面向什么场景、整体在做什么”，继而理解“怎么工作、独特之处在哪里、带来什么价值”？系统型还应能看出模块如何配合；单点型应能看出系统位置与痛点到效果的联系。来源没有回答的部分保留边界，不为补齐结构而编造。

<a id="motivation"></a>

### 背景/动机：沿原文论述展开

论文笔记的背景/动机应依据原文引言及必要的相关工作，保留作者提出问题的论述脉络：应用或研究需求是什么，已有方法为何不足，哪些困难促使作者提出本文思路。按论文实际逻辑组织，不强套固定步骤，也不只用一个直观例子或一句痛点替代整段动机。

凝练列出与本文动机直接相关的已有技术路线、代表性方案，以及各自的优点、局限或适用条件；适合比较时采用“技术路线｜代表方案｜优点/已有进展｜局限/条件”的短表。以原文讨论范围为主，不扩展成完整领域综述，不为填满表格而补造优缺点。

随后说明本文针对哪些不足提出了什么具体改变、为何能够起作用，即本文的突破点。区分作者的比较判断、实验支持的结论与助理分析；保留比较的时间和设置边界，不把个别方案的不足泛化到整条路线，也不为突出本文而强行贬低已有方法。

保持简洁，但讲清关键因果关系；方法细节留在方法章节。明确区分作者的论证与助理补充的解释，并附原文章节或链接。原文不可访问时注明依据交接材料及未核验范围，不把推测写成“原文认为”。

<a id="method"></a>

### 模型/方法：先整体框架，再展开细节

“模型/方法”开头先给出凝练的整体框架概述，交代输入输出、主要模块的职责及连接关系，再展开各模块、公式和关键机制。可采用系统框图、原文系统图，或“总体概述＋分点”的形式；不强制画图，也不只罗列模块名称。

若原文系统图已作为 banner，可在方法开头引用并补充简短流程说明，无需重复放同一张图。区分原文图与讨论示意图；训练流程和推理流程不同时应注明，避免读者将损失或优化步骤误认为推理模块。TL;DR 概括任务与贡献，不能替代方法部分对整体工作流程的交代。
