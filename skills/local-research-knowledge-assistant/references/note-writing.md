# 论文与技术笔记的写作约定

用于论文笔记和技术文章总结。论文材料与模板处理见[论文笔记流程](reading.md)；领域调研使用[报告写作约定](survey-writing.md)。本文件集中规定如何讲清任务、动机与机制，格式和归档不在这里重复。

## 先解释清楚，再压缩

默认读者有相关技术基础，但不熟悉这篇论文的术语和设计。先完成背景与方法的解释，再从正文提炼 TL;DR，最后套入模板。展示顺序仍是 TL;DR 在前，不等于写作时先定一段摘要再让正文配合它。已有用户亲写的 TL;DR 不在此流程中自动重写；有事实疑点单独指出。

凝练优先删重复和枝节，保留使读者理解所必需的因果、变量含义、模块衔接和条件。不要为了每点只写一句或每节等长，将解释压成术语串。用户深入追问的部分可以多展开，其余保持概括；不需要逐个解释所有实现模块或把单篇笔记写成领域综述。

三部分各有职责：TL;DR 让人快速把握整项工作；背景解释为什么值得这样设计；方法说明它具体怎样运行。共同概念可以简短呼应，但不要把同一段摘要复制三遍。

<a id="tldr"></a>

### TL;DR：读完能复述整项工作

开头先交代应用或研究情境，以及整体任务；必要时说明输入和输出。基础、理论工作描述研究目标，不虚构落地应用。随后用有联系的短段或要点讲清核心思路、相对已有做法的具体改变，以及产生的价值和必要条件。不强制固定条数。

- **系统性技术**：先概括整个系统在完成什么，再说明关键模块的属性、职责和协作。读者应知道信息或任务怎样在模块间传递；部署位置、接口、频率等只保留对理解系统必要且有依据的内容。
- **单点技术**：先说明它在更大流程中的位置，再串起具体瓶颈、改变了什么、为什么可能有效。不要为了套系统模板虚构多个模块。
- **共同要求**：技术名第一次出现时带出它在这里的作用；“采用 Transformer、引入多种先验、端到端优化”不能替代机制。独特贡献可以来自约束、信息利用、训练任务或模块协作，不只来自新网络。

TL;DR 可以概括一两个关键效果，但应交代必要条件，不用性能形容词或数字榜单替代思路。详细实验、实现参数和次要限制放正文；影响适用性的关键假设不能省略。只概括正文有依据的内容，不能把作者宣称或助理推断写成已独立验证的结论。新闻或非技术观点材料按事件和论点组织，不硬套上述技术结构。

<a id="motivation"></a>

### 背景/动机：说明本文思路如何被问题引出

依据原文引言及必要的相关工作，建立从研究需求到设计选择的联系：在什么任务和条件下，已有方法能做到什么，仍在哪里失败或付出代价，什么信息缺口、假设或计算过程造成了这一限制，本文据此改变了什么。按论文实际论述组织，不机械套固定句式。

与动机直接相关的技术路线和代表方案可用短表比较其进展、局限与适用条件；表格之后仍需解释哪一个缺口引出了本文的主要选择。仅列“前人有 A/B/C 三个不足”并接“本文提出 X”，没有说明 X 如何回应这些不足，不能视为动机已讲清楚。反之，也不要靠无关的领域发展史凑背景。

先正向解释研究需求和困难，再说明本文选择的合理性；细节留给方法。区分作者的论证、实验证据和助理补充分析，不将个别方案的不足泛化为整条路线，不为了突出本文而贬低已有方法。对关键比较附原文位置或链接；原文不可访问时，说明依据交接材料及未核验范围，不能声称“原文认为”。缺少成因证据时缩小结论，不能用流畅的因果句补造解释。

<a id="method"></a>

### 模型/方法：让读者能沿流程追踪信息

开头用一段总体说明或“概述＋流程”交代输入、目标输出、主要中间结果，以及关键模块怎样连接。必要时区分已知条件、需要预测的量和可以学习的参数。箭头图或模块名单只帮助定位，不能替代对每一步产生什么、供下一步做什么的解释。

随后围绕决定论文贡献的机制展开，而非逐个抄模块简介。对关键步骤回答：它接收什么信息，对什么对象执行什么操作或施加什么约束，得到的变化怎样进入后续计算，为什么对应背景中的困难。相关细节包括信息来源、绑定或对应关系、优化目标、条件注入位置等；按论文实际贡献取舍，不要求为每个模块填同一张表。

例如，“用注意力融合多帧特征以增强一致性”仍需查清哪些帧交换何种信息、融合结果怎样影响输出、是否另有对应监督或一致性约束。查不到这些细节时标明缺口，不凭架构常识补齐；模型拥有某种表示能力也不等于实验已证明该问题被解决。

公式用于解释关键操作时，说明符号、变量来源、约束对象和在流程中的作用；不要孤立列式。区分训练时用于获得参数的监督与损失，以及推理时实际执行的步骤；逐场景优化或在线更新的方法按其真实流程说明，不硬套训练/推理二分。主体流程在方法中讲清，具体训练日程、超参数和完整实验表留到对应章节。

原文系统图已放在 banner 时，在方法开头引用并补充流程说明，不重复放图。图中文字或公式不能代替正文解释；示意图、举例和助理推断需与原文内容区分。先说明方法实际做了什么，再在确有混淆处简短澄清；不要让连续的“不是……”和局限声明打断主线。

## 成稿自查：看理解结果，不只看标题齐全

| 阅读检查 | 不通过时处理 |
|---|---|
| 只看 TL;DR，能否用自己的话复述任务、核心做法和独特价值？ | 补齐技术定位及机制之间的联系；移走过细参数，解释承担关键作用的术语 |
| 看完背景，能否说明为什么原有做法在这些条件下不足，本文选择怎样回应？ | 回查动机和成因，补上设计联系；证据不足则收窄论断 |
| 看完方法，能否追踪一次输入到输出，并指出关键步骤如何改变结果？ | 补齐中间量、操作和模块衔接；区分推理流程、优化步骤与训练监督 |
| 用户关心的问题是否有明确答案或可定位的未解决项，且关键解释没有在压缩中丢失？ | 将回答融入相应章节，保留必要细节；不额外复制问答或纠错清单 |

自查用于修订成稿，不输出另一份质量审查章节。保留来源、假设和不确定性；方法合理、文字清楚都不等于已复现实验。局部修订只检查受影响内容及其衔接，保留人工段落和已认可的结构。
