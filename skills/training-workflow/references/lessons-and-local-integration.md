| 实例 | 下一次应做的事 |
| --- | --- |
| 训练清单正确，分布式sampler却因各rank划分种子/epoch问题长期只覆盖子集 | 检查实际各rank样本和完整epoch覆盖，不仅比清单 |

| 冻结相机头，但共享主干仍更新 | 核对输出与梯度路径；参数不变不代表相机估计不变 |

| 修复前后续训混在一起会误导对照 | 独立版本/入口快照、标注继承模型及优化器历史，保留原检查点和评估 |
| 每5分钟唤醒模型检查“是否正常”浪费token | 正常运行由脚本判断，质量检查和异常分析才用模型 |
| Codex外部进程遇到active writer无法接管；queue --resume曾在失败后丢队列 | 验证持久化和唤醒分别成功；本地经验是先入队再显式resume/start，由脚本检查派发回执并退避重试（旧小时模型兜底已非默认）；不盲目复制CLI/API版本 |
| 飞书请求成功与用户手机提醒不同 | 留回执并确认首次测试到达，区分客户端免打扰等配置 |
| 训练结束标签不保证最终评估结束；仅写自然语言“停止”不够 | 实现产物/队列核验及通知后关闭任务的持久化状态机 |

## 2026-10-31：分段停止后的轮次偏移

Lightning 在轮次中途 should_stop 后保存的 epoch 可能已增加，但数据逻辑轮次尚未完成。仅验证恢复后的头几步会漏掉问题：本次 C4 在500步停下，恢复后的501—729正常，第730步才跳过一轮。恢复测试应越过至少一个数据轮次边界，并覆盖重复停止/恢复；将真实样本、视角和形状序列与连续运行逐条比较。

本次通过记录 checkpoint_epoch 与 floor(resume_step/epoch_length) 的偏移校正 sampler，并增加所有rank同步的更新前游标检查。偏移计算只适用于已确认的一次更新对应一个采样批次协议；梯度累积、变长数据、改变world size等需另行定义数据游标。验证应加载与生产相同的环境入口，避免CUDA扩展缓存差异干扰故障定位。
